## No user images anywhere in the portal

The portal handles **no user images**. It does not accept, store, process, proxy, resize, or display any uploaded picture, and it performs **no Storage access at all**: no bucket, no object read or write, no signed URL, no image proxy route, and no image-processing dependency.

`app_profiles.profile_photo_path` remains a pre-existing legacy column owned by the desktop application and its retained v1 profile RPC. Its rows and values are untouched: the portal simply never selects it, never projects it, and never writes it. No migration was added, no row was deleted, and no value was cleared.

## Account security surface

- Portal authentication is now Azure Account API-backed in source. `/login`, `/signup`, `/forgot-password`, `/auth/confirm`, and `/reset-password` no longer require Supabase browser configuration or Supabase SSR clients.
- `QT_ACCOUNT_API_URL` is the only portal auth endpoint. Production requires it to be an HTTPS URL with no credentials, query string, or fragment. Local development may use the Functions host fallback.
- Password sign-in writes HttpOnly `qt-session` and `qt-refresh` cookies only through the Azure server client. Provider errors are mapped to either a generic credential rejection or a generic secure sign-in outage; passwords, tokens, and provider details never enter returned page state.
- Account API session lifecycle hooks register, heartbeat, and end the current portal session with server-generated idempotency keys. These hooks are best effort and must not block login, logout, or protected renders during an Account API telemetry outage.
- Reauthentication uses an isolated Azure auth client, not the request-bound session client, so a current-password check cannot rotate or downgrade the caller's browser cookies. Ambiguous provider responses fail as unavailable rather than as a wrong password.
- Password change is implemented through the Azure Account API after same-origin, assurance, verified caller, current-password, and bearer-token checks. Email change and TOTP enrollment/verification/removal are intentionally source-locked until Azure SQL owns the required confirmation/factor/AAL2 contracts.
- The current assurance state is password-only for Azure auth. All mutating Server Actions still call the same assurance guard before credential, Account API, or Azure SQL writes, and the TOTP UI returns unavailable rather than trusting `app_profiles.two_factor_enabled` or any client flag.
- Signup confirmation accepts one bounded Azure token and redirects only to login notices. Password reset accepts one bounded Azure reset token, updates through the Azure Account API, clears the browser recovery marker after success, and never leaves an authenticated portal session behind.
- The enforced CSP permits the Cloudflare challenge host and Azure Functions endpoints, not Supabase. Credential and callback routes remain private/no-store.
- Legacy Supabase references that remain in this document describe desktop-owned schema/migration history or migration evidence, not the current portal login path.

Success requires the receipt to echo the caller UUID and `expectedVersion + 1`; `revision_conflict` returns the committed version when available.

The rejection triggers are narrow (a tampered version token, a tampered checkbox value, or one bounded text/phone violation), and the stale path deliberately relies on that reset to pull the other session's committed values in rather than letting a retry overwrite them. ## Account API (Task 8, source only)

- A separate Azure Functions package at `cloud/azure/account_function/` in the desktop repository, with staging infrastructure as code. Nothing is deployed and no Azure resource exists; `azure.account-api-contract` and `azure.account-infrastructure` are source evidence only, and both say so in their own check evidence.
- The package is modular and its Azure adapter holds no rules: authorization, RBAC, idempotency, profile read/update, session lifecycle, notifications, the disabled email worker contract, report queues, private artifact download signing, account lifecycle state, and audit all live behind testable boundaries, which is why 371 offline Account API tests cover them without requiring managed services. The preflight check refuses an adapter that decides authorization and refuses a pure module that imports the Azure SDK.
- Routes are published under `api/v1`, matching the `QT_ACCOUNT_API_URL` base the portal is already configured with, and `GET /api/v1/health` is unauthenticated so the integrated probe can reach it. Health reports whether dependencies are _configured_, never whether a credential is valid.
- Roles are read from both stores and reconciled; neither is written. The legacy blob registry can only express `admin`, `support` and `user`, so a database Owner reads back as Admin or is absent — reported as an expected projection, not as drift. Only `missing-in-database` and `divergent` block retiring the blob. Retirement is certified only when the blob document itself was read and yielded at least one canonical entry: blob readability is tracked separately from the merged registry, so the bootstrap administrators folded in from `QT_ADMIN_USER_IDS` cannot make an unread blob look like a read one.
- `QT_BREAK_GLASS_OWNER_IDS` holds reviewed Owner UUIDs, immutable through the API and reported on every request that uses them. No role-mutating route exists yet: it lands after a tenancy's reconciliation report is clean.
- Idempotency reserves its key before the write through an atomic conditional create that resolves expiry in the same step, scopes reservations per caller, and refuses to release a completed outcome, so neither a request killed between the insert and the record nor two concurrent attempts can append a second row to a table with no update and no delete. Reservation leases and replay windows are separate settings: one number would force a choice between stranding a killed attempt for a day and expiring a lease mid-attempt. A dependency failure that provably never delivered the request (`upstream_unreachable`) releases the key, because a retry then cannot duplicate; anything that may have committed keeps it. The store is still process-local, which is why the staging template pins the scale limit to one instance rather than only describing the constraint; a durable store is what lifts it.
- Audit event types are allow-listed rather than only regex-bounded, so a Support caller cannot append rows that impersonate another subsystem's events into an append-only trail. A failed legacy mirror is reported in the response instead of swallowed.
- The role report withholds break-glass-only identities from a caller that cannot grant Owner, and reports the legacy entry counts so an empty registry is distinguishable from an agreeing one. `QT_ADMIN_USER_IDS` — the legacy function's immutable bootstrap admin set — is read into the reconciliation, because those administrators appear in no blob document and would otherwise fall into no mismatch class. Registry keys that are not UUIDs are refused, counted, and block retirement, so a store is never retired on the strength of entries nobody could reconcile.
- Known limitations carried deliberately: the store is process-local, there is no request-rate limiting, and nothing has been verified against Azure SQL, Storage, Azure Functions, or ARM. The Bicep template has not been linted or deployed, and Azure SQL/auth secrets would land in app settings as plaintext unless moved to Key Vault references.
- Every Account API structural boolean is classified as fully pinned or construct-only in `account-api-analysis.ts`, because an unclassified boolean reads as a stronger claim than it is. These source checks reject the specific defects they were written against without proving live provider, Azure, or ARM behavior.

## Safe validation

A standalone portal clone runs:

```bash
npm run validate:portal
npm run test:e2e
```

The integrated workspace additionally runs:

```bash
npm run validate
npm run preflight:strict
```

`preflight:strict` exits unsuccessfully while `productionReady` remains false; warnings and blockers therefore cannot unlock production. Offline preflight reads the eleven explicit migration files, performs source-only structural lifecycle/profile checks, evaluates the exported Next.js header rules, and inspects only process-environment names/status. It never opens real `.env` files, emits configured values, connects to PostgreSQL, touches any Storage service, or mutates cloud resources.

## Production gate

Production is intentionally **NO-GO**. Production mutations require authorized staging evidence, PostgreSQL/pgTAP execution, the future Azure Account API and RBAC parity, a current backup/rollback package, and a separate explicit go/no-go confirmation.
