# Staging readiness — source baseline

Date: 2026-09-02

This document records non-secret source findings only. No production setting, database, DNS record, Vercel project, Azure resource, Supabase project, or user record was changed.

## No user images anywhere in the portal

The portal handles **no user images**. It does not accept, store, process, proxy, resize, or display any uploaded picture, and it performs **no Storage access at all**: no bucket, no object read or write, no signed URL, no image proxy route, and no image-processing dependency.

`app_profiles.profile_photo_path` remains a pre-existing legacy column owned by the desktop application and its retained v1 profile RPC. Its rows and values are untouched: the portal simply never selects it, never projects it, and never writes it. No migration was added, no row was deleted, and no value was cleared.

## Account security surface (Task 7)

- Every change to the account's credentials or factors requires the current password: password change, verified email change, authenticator enrollment, and authenticator removal all reauthenticate first, and each one refuses to proceed unless the provider positively confirms the credential. Enrollment is included deliberately — verifying a factor raises the required assurance level for every session of the account, so an attacker who could enroll their own authenticator would push the owner into the identity-verified support path.
- Assurance is enforced on mutations, not only on rendering, with one documented exception below (password recovery). Every Server Action that changes the account — the five security actions plus profile and preferences — asks `requireMutationAssurance` for a decision before it verifies a password or touches anything, and refuses a session that still owes its second factor. This is not redundant with the route guards: a Server Action is its own endpoint, the proxy admits any session that has a user and knows nothing about assurance levels, and reauthentication is no defense against an attacker whose starting position is knowing the password.
- The AAL1 session cookie written by the password step survives an `mfa-required` response on purpose: the provider's challenge and verify calls act on that session, so clearing it would make the second factor unsatisfiable. It is a ticket to finish signing in, not a signed-in session — every protected route redirects it to the challenge and every account mutation refuses it.
- The credential-rejection code set has exactly one definition, shared by sign-in and reauthentication. An error carrying no machine-readable code is classified as unavailable rather than as a wrong password, so an ambiguous provider response never becomes a false "that password is not correct" and never lets a mutation through.
- Reauthentication runs on a session-isolated Supabase client that persists nothing, refreshes nothing, and writes no cookie. This matters beyond hygiene: running the verification sign-in on the request-bound client would overwrite the caller's session and could silently downgrade a verified AAL2 session to AAL1.
- A transport failure during reauthentication is reported as unavailable, never as success and never as a wrong password, so an outage cannot be used to slip past the check.
- Two-factor state is derived only from Supabase factors the provider reports as `verified`. `app_profiles.two_factor_enabled` is a desktop-owned legacy column and is deliberately never read or written by the portal, so there is no second source of truth to disagree with the provider.
- Enrollment is enforced, not decorative. When a verified factor exists, the password step alone returns a challenge instead of a session redirect, and every protected account route refuses an AAL1 session until the challenge is satisfied.
- The challenge decision is built only from things the caller cannot forge. The level a session has reached comes from the `aal` claim inside the signed access token; the level this account's factors _require_ is computed from `mfa.listFactors`, which the pinned client answers through `getUser()` — a network call the provider authenticates. The provider helper's own `nextLevel` is deliberately ignored: it derives from `session.user.factors`, which on the server comes out of the request cookie with no signature (the pinned client wraps that object in a "may not be authentic" warning proxy), so trusting it would let a caller switch the entire second-factor requirement off by deleting one key from their own cookie.
- Availability failures are split by what they actually cost. A mutation refuses unless both halves of the decision were readable: an unread factor list cannot be treated as "no factors", and an unread level cannot be treated as "high enough". Page rendering is deliberately more permissive — it redirects only on a positive challenge requirement — because a transport blip must not lock an owner out of their own account, and a redirect to a challenge that cannot be described could loop. The security page reports two-factor status as temporarily unavailable rather than as "password only" when the factor list could not be read.
- Abandoned unverified enrollments are removed before a new enrollment begins. Enrollment confirmation challenges only a factor the provider reports as this caller's pending enrollment, and removal refuses any factor the provider does not currently report as verified: no factor id in the change is ever trusted from a form. The portal caps enrollment at one verified authenticator so the sign-in challenge and the removal controls address a factor unambiguously; the security page renders a separate removal control per factor, so factors enrolled outside the portal can still all be removed, and the sign-in challenge tries each verified factor rather than only the first.
- The TOTP secret and QR payload exist only in the enrollment action state until the factor is verified. They are never logged, never persisted by the portal, and the QR is rendered only when the payload is a real image data URI.
- Verified email change requires confirmation from both the current and the new address. The callback destination is bound to the redirect type the pinned client actually emits, which is a two-valued signal: `@supabase/auth-js` reads it back from the stored PKCE verifier and appends a type only for password recovery, so a signup or `updateUser({ email })` confirmation exchanges to `null`. Both non-recovery flows are therefore bound to `null` and refuse `"recovery"`. This is verified, not assumed: `tests/lib/auth-exchange-contract.test.ts` drives the real client with an in-memory storage adapter and a stubbed fetch and asserts the emitted value for all three link kinds. The escalation that matters is closed in both directions — `/reset-password` is the only destination that authorizes a password change without the current password, and only a recovery exchange can reach it.
- Password change signs other sessions out on a best-effort basis. The change still reports success if that cleanup fails, because the password is already rotated, and the success copy is conditional on the actual cleanup result: it claims other sessions were signed out only when the provider confirmed it, and otherwise tells the owner to sign out from each device they still trust.
- The session minted by each reauthentication is revoked, not abandoned. In the pinned client `_signOut` posts `/logout?scope=<scope>` for every scope, including `local`, so the verification client's `signOut({ scope: "local" })` does ask the provider to revoke the session it just created; only that request failing would leave a refresh token alive until expiry, and such a token is never written to a cookie, a log, or a store. `scope: "global"` is still refused here because it would sign the owner out of every device on a mere password check. Whether the revocation is honoured server-side is provider behavior and remains unverified below.
- The PKCE flow id is not forwarded to the exchange, because the pinned client only appends `sb_flow_id` to a redirect URL when `experimental.appendPkceFlowIdToRedirects` is enabled, and it is not. The confirm route therefore reads the fixed verifier key, which mirrors the most recently started flow: starting a second PKCE flow (say a password reset) before using the first link invalidates the first link. Enabling the experimental option would fix it but changes the redirect URL the provider must accept, so it needs a verified redirect allow-list in staging first.
- Password recovery is the one account mutation that is not assurance-gated, and that is deliberate. `resetPassword` is authorized by possession of the verified inbox plus the consumed recovery marker, and gating it on a satisfied second factor would make an owner who lost their password unable to recover at all. What stops a recovery link from becoming account access does not depend on any provider assumption: after the update, `resetPassword` clears the portal's Supabase auth cookies and redirects to the login page, so the recovery exchange leaves no usable session behind and the second factor is then required at sign-in like any other visit. (That a recovery exchange also produces an AAL1 session is provider behavior and is listed as unverified below; it is a second line of defence, not the load-bearing one.)
- Recovery guidance is explicit that this portal issues no printable recovery codes, so a lost authenticator needs identity-verified support review rather than a self-service bypass.

## Verified from source

- The portal has exact dependency pins, tests, enforced challenge-compatible CSP plus baseline security headers, environment allow-list validation, Supabase SSR login/logout, website signup, PKCE confirmation bound to Supabase's trusted runtime redirect type, generic recovery/reset guarded by a consumed UUID/access-token-bound browser marker, source consent metadata, Supabase-managed CAPTCHA submission, protected account routing, and UUID-scoped DAL/DTO boundaries.
- The five-minute recovery marker closes ordinary-session reset access in the normal browser flow, but it uses the exchanged bearer token rather than a portal secret and has no atomic server nonce store. Source evidence therefore does not claim malicious bearer-token resistance or globally atomic one-time consumption.
- The desktop-owned ordered eleven-migration ledger represents immutable UUID identity, canonical Owner/Admin/Support/User roles, session inventory, append-only auth events, grants, RLS contracts, additive positive profile versions, an every-UPDATE version trigger, the retained legacy v1 profile mutation, and the identity-bound versioned v2 CAS RPC.
- The portal preflight assembles its structural schema evidence from an explicit eleven-file allow-list, while integrity observation enumerates the desktop `supabase/migrations` directory so an unpinned extra file cannot hide. Source integrity is proven by exact SHA-256 digests of the raw migration bytes: `supabase.migration-integrity` pins all eleven filename/digest pairs, and the collector enumerates the desktop `supabase/migrations` directory rather than only the pinned names, so an unpinned extra migration is reported instead of being invisible. Unavailable, incomplete, reordered, renamed, duplicated, extra, and drifted artifacts all block, which closes `sourceReady` on any byte change, including whitespace, comments, dynamic SQL, or inert additions.
- All eleven digests are pinned to the reviewed migration bytes and duplicated literally in the focused tests, so a production edit alone cannot repin one.
- The remaining structural SQL checks in `supabase.profile-contract` are untrusted defense-in-depth only. They can show that reviewed constructs are present; they are not evidence that arbitrary later SQL is safe. They make no bucket, Storage-policy, or photo claim of any kind. The retained legacy v1 argument list is asserted verbatim, including its legacy photo argument, purely to confirm the desktop-owned function was not altered.
- Portal profile source covers owner-scoped profile and preferences reads, forms, and Server Actions with optimistic profile-version receipts. Focused tests cover bounded input, stale and malformed receipts, provider failures, cross-owner rows, and generic unavailable errors.
- Profile and preferences mutations accept exactly two RPC envelope shapes. Success requires `error === null` plus one exact three-field receipt — `user_id`, `profile_version`, `updated_at` — whose owner UUID and `expectedVersion + 1` match, with any extra key rejected. Definitive staleness requires `data === null` with string error code `40001`. A missing or undefined `error`, a mixed data-plus-error pair, a numeric `40001`, a malformed receipt, a receipt still carrying a retired photo field, and a thrown call are all service failures that never report success.
- Authenticated loading distinguishes failure classes, and both guards on a route agree. `loadAccountProfile` and `loadAccountOverview` return `null` only when Auth reports no verified user, so `requireCurrentProfile` and `requireCurrentAccount` redirect only on that `null`. Provider errors, absent rows, malformed or cross-owner DTOs, transport throws, unusable identities, and server-client factory failures raise generic server-only unavailable errors, so an authenticated visitor sees a generic error page instead of a misleading login redirect and no provider detail is exposed. A root `src/app/error.tsx` renders failures raised by the account layout guard, and a route-segment `src/app/account/error.tsx` renders page-guard failures while keeping the account shell; a sibling boundary cannot catch its own layout's throw, which is why both exist. A cross-owner profile row is degraded rather than displayed.
- A stale compare-and-swap now returns the committed profile version and revalidates the read route, so the visitor can retry immediately instead of reloading by hand. When the committed version cannot be established exactly, the form keeps its existing token rather than guessing.
- Existing `AccountNavigation`, account layout, and keyboard-focus component tests are fixture-safe authenticated-route accessibility evidence. They do not add a production authentication bypass and are not live staging evidence.
- Playwright covers the unauthenticated `/account` redirect and axe-scans the four credential routes. `/account/profile` and `/account/preferences` therefore ship with component-level accessibility tests but **no end-to-end axe scan and no live save**, because an authenticated browser fixture needs an authorized managed project. Add both during staging verification.
- Known limitation: React resets the uncontrolled account form fields once a Server Action resolves, so a rejected submit restores the stored values while asking the visitor to review the highlighted field. The rejection triggers are narrow (a tampered version token, a tampered checkbox value, or one bounded text/phone violation), and the stale path deliberately relies on that reset to pull the other session's committed values in rather than letting a retry overwrite them. Echoing submitted values back would change all six portal forms and is deferred.
- The desktop remains the current Azure/Supabase schema owner. The dedicated Account API is not implemented or deployed yet.
- The marketing website has its Vercel/theme source contract.

## Unknown until authorized staging access is available

- **Task 7 provider behavior is unverified against a live project.** No Supabase project has been contacted, so the following are assumptions from the pinned client library and its documentation, not evidence: that a secure email change emails both addresses; that `mfa.enroll` returns a `qr_code` usable as an image source; that `signInWithPassword` on an isolated client leaves the caller's session untouched in practice; that `signOut({ scope: "others" })` revokes the intended sessions; that `mfa.verify` persists the upgraded AAL2 session through the SSR cookie adapter; and that AAL transitions behave as `getAuthenticatorAssuranceLevel` reports. The exchange `redirectType` is deliberately _not_ in this list: it is decided inside the pinned dependency and is pinned by a contract test against the real client, not by assumption.
- A failed assurance read is deliberately silent, and that has a portal-wide consequence worth naming: if the factor inventory cannot be read, or the access token carries no recognized `aal` claim, then _every_ account mutation — profile and preferences included, even for an account with no factor enrolled — answers "temporarily unavailable" while protected routes still render. That is the intended fail-closed choice, but nothing logs it and preflight cannot see runtime state, so it is indistinguishable from a provider outage from the outside. Add a degradation signal alongside the Task 8 account API, which is the first component allowed to hold server-side logging or a privileged key.
- Whether the provider emits an `aal` claim on every access token, and whether a recovery exchange yields an AAL1 session, are unverified provider behaviors that the point above depends on.
- Provider rate limits on password verification and TOTP challenges are unknown. Repeated reauthentication attempts could be throttled, which this portal would surface as "temporarily unavailable".
- Whether Supabase's "Secure email change" project setting is enabled is unverified. With it disabled, only the new address would confirm, which weakens the guarantee the security page states.
- Server-sent security notification email is **not implemented**. The portal relies on Supabase's own recovery and email-change messages plus in-app notices; anything portal-originated needs the Task 8 account API, because no mail credential may exist in this repository.
- No authenticated end-to-end coverage exists for `/account/security`, so the enrollment, challenge, and removal journeys are verified at the unit and component level only.

- Migration execution and validation against PostgreSQL catalogs, including `profile_version`, the unconditional trigger, retained legacy v1 behavior, the exact v2 identity/CAS/SQLSTATE/receipt/EXECUTE contract, and concurrent stale-write behavior.

## Safe validation

A standalone portal clone runs:

```bash
npm run validate:portal
npm run test:e2e
```

The integrated workspace additionally runs:

```bash
npm run validate
npm run preflight:strict
```

`preflight:strict` exits unsuccessfully while `productionReady` remains false; warnings and blockers therefore cannot unlock production. Offline preflight reads the eleven explicit migration files, performs source-only structural lifecycle/profile checks, evaluates the exported Next.js header rules, and inspects only process-environment names/status. It never opens real `.env` files, emits configured values, connects to PostgreSQL, touches any Storage service, or mutates cloud resources.

## Production gate

Production is intentionally **NO-GO**. Production mutations require authorized staging evidence, PostgreSQL/pgTAP execution, the future Azure Account API and RBAC parity, a current backup/rollback package, and a separate explicit go/no-go confirmation.
