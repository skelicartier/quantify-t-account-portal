## Account security surface (Task 7)

- Every change to the account's credentials or factors requires the current password: password change, verified email change, authenticator enrollment, and authenticator removal all reauthenticate first, and each one refuses to proceed unless the provider positively confirms the credential. Enrollment is included deliberately — verifying a factor raises the required assurance level for every session of the account, so an attacker who could enroll their own authenticator would push the owner into the identity-verified support path.
- Assurance is enforced on mutations, not only on rendering, with one documented exception below (password recovery). Every Server Action that changes the account — the five security actions plus profile and preferences — asks `requireMutationAssurance` for a decision before it verifies a password or touches anything, and refuses a session that still owes its second factor. This is not redundant with the route guards: a Server Action is its own endpoint, the proxy admits any session that has a user and knows nothing about assurance levels, and reauthentication is no defense against an attacker whose starting position is knowing the password.
- The AAL1 session cookie written by the password step survives an `mfa-required` response on purpose: the provider's challenge and verify calls act on that session, so clearing it would make the second factor unsatisfiable. It is a ticket to finish signing in, not a signed-in session — every protected route redirects it to the challenge and every account mutation refuses it.
- The credential-rejection code set has exactly one definition, shared by sign-in and reauthentication. An error carrying no machine-readable code is classified as unavailable rather than as a wrong password, so an ambiguous provider response never becomes a false "that password is not correct" and never lets a mutation through.
- Reauthentication runs on a session-isolated Supabase client that persists nothing, refreshes nothing, and writes no cookie. This matters beyond hygiene: running the verification sign-in on the request-bound client would overwrite the caller's session and could silently downgrade a verified AAL2 session to AAL1.
- A transport failure during reauthentication is reported as unavailable, never as success and never as a wrong password, so an outage cannot be used to slip past the check.
- Two-factor state is derived only from Supabase factors the provider reports as `verified`. `app_profiles.two_factor_enabled` is a desktop-owned legacy column and is deliberately never read or written by the portal, so there is no second source of truth to disagree with the provider.
- Enrollment is enforced, not decorative. When a verified factor exists, the password step alone returns a challenge instead of a session redirect, and every protected account route refuses an AAL1 session until the challenge is satisfied.
- The challenge decision is built only from things the caller cannot forge. The level a session has reached comes from the `aal` claim inside the signed access token; the level this account's factors _require_ is computed from `mfa.listFactors`, which the pinned client answers through `getUser()` — a network call the provider authenticates. The provider helper's own `nextLevel` is deliberately ignored: it derives from `session.user.factors`, which on the server comes out of the request cookie with no signature (the pinned client wraps that object in a "may not be authentic" warning proxy), so trusting it would let a caller switch the entire second-factor requirement off by deleting one key from their own cookie.
- Availability failures are split by what they actually cost. A mutation refuses unless both halves of the decision were readable: an unread factor list cannot be treated as "no factors", and an unread level cannot be treated as "high enough". Page rendering is deliberately more permissive — it redirects only on a positive challenge requirement — because a transport blip must not lock an owner out of their own account, and a redirect to a challenge that cannot be described could loop. The security page reports two-factor status as temporarily unavailable rather than as "password only" when the factor list could not be read.
- Abandoned unverified enrollments are removed before a new enrollment begins. Enrollment confirmation challenges only a factor the provider reports as this caller's pending enrollment, and removal refuses any factor the provider does not currently report as verified: no factor id in the change is ever trusted from a form. The portal caps enrollment at one verified authenticator so the sign-in challenge and the removal controls address a factor unambiguously; the security page renders a separate removal control per factor, so factors enrolled outside the portal can still all be removed, and the sign-in challenge tries each verified factor rather than only the first.
- The TOTP secret and QR payload exist only in the enrollment action state until the factor is verified. They are never logged, never persisted by the portal, and the QR is rendered only when the payload is a real image data URI.
- Verified email change requires confirmation from both the current and the new address. The callback destination is bound to the redirect type the pinned client actually emits, which is a two-valued signal: `@supabase/auth-js` reads it back from the stored PKCE verifier and appends a type only for password recovery, so a signup or `updateUser({ email })` confirmation exchanges to `null`. Both non-recovery flows are therefore bound to `null` and refuse `"recovery"`. This is verified, not assumed: `tests/lib/auth-exchange-contract.test.ts` drives the real client with an in-memory storage adapter and a stubbed fetch and asserts the emitted value for all three link kinds. The escalation that matters is closed in both directions — `/reset-password` is the only destination that authorizes a password change without the current password, and only a recovery exchange can reach it.
- Password change signs other sessions out on a best-effort basis. The change still reports success if that cleanup fails, because the password is already rotated, and the success copy is conditional on the actual cleanup result: it claims other sessions were signed out only when the provider confirmed it, and otherwise tells the owner to sign out from each device they still trust.
- The session minted by each reauthentication is revoked, not abandoned. In the pinned client `_signOut` posts `/logout?scope=<scope>` for every scope, including `local`, so the verification client's `signOut({ scope: "local" })` does ask the provider to revoke the session it just created; only that request failing would leave a refresh token alive until expiry, and such a token is never written to a cookie, a log, or a store. `scope: "global"` is still refused here because it would sign the owner out of every device on a mere password check. Whether the revocation is honoured server-side is provider behavior and remains unverified below.
- The PKCE flow id is not forwarded to the exchange, because the pinned client only appends `sb_flow_id` to a redirect URL when `experimental.appendPkceFlowIdToRedirects` is enabled, and it is not. The confirm route therefore reads the fixed verifier key, which mirrors the most recently started flow: starting a second PKCE flow (say a password reset) before using the first link invalidates the first link. Enabling the experimental option would fix it but changes the redirect URL the provider must accept, so it needs a verified redirect allow-list in staging first.
- Password recovery is the one account mutation that is not assurance-gated, and that is deliberate. `resetPassword` is authorized by possession of the verified inbox plus the consumed recovery marker, and gating it on a satisfied second factor would make an owner who lost their password unable to recover at all. What stops a recovery link from becoming account access does not depend on any provider assumption: after the update, `resetPassword` clears the portal's Supabase auth cookies and redirects to the login page, so the recovery exchange leaves no usable session behind and the second factor is then required at sign-in like any other visit. (That a recovery exchange also produces an AAL1 session is provider behavior and is listed as unverified below; it is a second line of defence, not the load-bearing one.)
- Recovery guidance is explicit that this portal issues no printable recovery codes, so a lost authenticator needs identity-verified support review rather than a self-service bypass.

## Account API (Task 8, source only)

- A separate Azure Functions package at `cloud/azure/account_function/` in the desktop repository, with staging infrastructure as code. Nothing is deployed and no Azure resource exists; `azure.account-api-contract` and `azure.account-infrastructure` are source evidence only, and both say so in their own check evidence.
- The package is modular and its Azure adapter holds no rules: authorization, RBAC, idempotency, session lifecycle, notifications, the disabled email worker contract, report queues, private artifact download signing, account lifecycle state, and audit all live behind testable boundaries, which is why 358 offline Account API tests cover them without requiring managed services. The preflight check refuses an adapter that decides authorization and refuses a pure module that imports the Azure SDK.
- Routes are published under `api/v1`, matching the `QT_ACCOUNT_API_URL` base the portal is already configured with, and `GET /api/v1/health` is unauthenticated so the integrated probe can reach it. Health reports whether dependencies are _configured_, never whether a credential is valid.
- Roles are read from both stores and reconciled; neither is written. The legacy blob registry can only express `admin`, `support` and `user`, so a database Owner reads back as Admin or is absent — reported as an expected projection, not as drift. Only `missing-in-database` and `divergent` block retiring the blob. Retirement is certified only when the blob document itself was read and yielded at least one canonical entry: blob readability is tracked separately from the merged registry, so the bootstrap administrators folded in from `QT_ADMIN_USER_IDS` cannot make an unread blob look like a read one.
- `QT_BREAK_GLASS_OWNER_IDS` holds reviewed Owner UUIDs, immutable through the API and reported on every request that uses them. No role-mutating route exists yet: it lands after a tenancy's reconciliation report is clean.
- Idempotency reserves its key before the write through an atomic conditional create that resolves expiry in the same step, scopes reservations per caller, and refuses to release a completed outcome, so neither a request killed between the insert and the record nor two concurrent attempts can append a second row to a table with no update and no delete. Reservation leases and replay windows are separate settings: one number would force a choice between stranding a killed attempt for a day and expiring a lease mid-attempt. A dependency failure that provably never delivered the request (`upstream_unreachable`) releases the key, because a retry then cannot duplicate; anything that may have committed keeps it. The store is still process-local, which is why the staging template pins the scale limit to one instance rather than only describing the constraint; a durable store is what lifts it.
- Audit event types are allow-listed rather than only regex-bounded, so a Support caller cannot append rows that impersonate another subsystem's events into an append-only trail. A failed legacy mirror is reported in the response instead of swallowed.
- The role report withholds break-glass-only identities from a caller that cannot grant Owner, and reports the legacy entry counts so an empty registry is distinguishable from an agreeing one. `QT_ADMIN_USER_IDS` — the legacy function's immutable bootstrap admin set — is read into the reconciliation, because those administrators appear in no blob document and would otherwise fall into no mismatch class. Registry keys that are not UUIDs are refused, counted, and block retirement, so a store is never retired on the strength of entries nobody could reconcile.
- Known limitations carried deliberately: the store is process-local, there is no request-rate limiting, and nothing has been verified against Supabase, Azure, Storage, or ARM. The Bicep template has not been linted or deployed, and the service-role key lands in app settings as plaintext (the standard Azure model; the managed identity a Key Vault reference needs is already defined).
- Every Account API structural boolean is classified as fully pinned or construct-only in `account-api-analysis.ts`, because an unclassified boolean reads as a stronger claim than it is. These source checks reject the specific defects they were written against without proving live provider, Azure, or ARM behavior.

## Safe validation

A standalone portal clone runs:

```bash
npm run validate:portal
npm run test:e2e
```

The integrated workspace additionally runs:

```bash
npm run validate
npm run preflight:strict
```

`preflight:strict` exits unsuccessfully while `productionReady` remains false; warnings and blockers therefore cannot unlock production. Offline preflight reads the eleven explicit migration files, performs source-only structural lifecycle/profile checks, evaluates the exported Next.js header rules, and inspects only process-environment names/status. It never opens real `.env` files, emits configured values, connects to PostgreSQL, touches any Storage service, or mutates cloud resources.

## Production gate

Production is intentionally **NO-GO**. Production mutations require authorized staging evidence, PostgreSQL/pgTAP execution, the future Azure Account API and RBAC parity, a current backup/rollback package, and a separate explicit go/no-go confirmation.
